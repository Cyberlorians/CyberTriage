# Deployment Step By Step

This guide is written slowly on purpose. The goal is that a new analyst can follow it without already knowing every Azure term.

## Before You Start

Do not start with a real incident.

Start with one test machine that is active in Microsoft Defender for Endpoint.

You need these names ready:

```text
Azure subscription ID
Resource group for playbooks
Region
Sentinel workspace name
Sentinel workspace resource group
Sentinel workspace customer ID
Storage account name
Storage container name
Notification email
MDE device ID for one test machine
```

## Step 1: Pick The Cloud

Choose one:

```text
Commercial Azure
GCCH / Azure Government
```

Commercial is the validated lab path in this repo.

GCCH has draft templates and endpoint notes, but must be verified in a GCCH tenant before production use.

## Step 1A: Use The Full Commercial Deployment Button

For commercial Azure, start with the full deployment template unless you have a reason to deploy each piece separately.

Use an account that is `Owner` on the subscription. That lets the template create the resources and assign Azure RBAC roles to the managed identities automatically.

The full template deploys these resources into the resource group you choose:

```text
Evidence storage account and cybertriage-results container
SAS broker Function App: name entered during deployment
CyberTriage-LiveResponse-Collection
Set-CyberTriage
Check-CyberTriageQueue
Function host storage account
API connections used by the Logic Apps
Azure RBAC role assignments for the managed identities
```

[![Deploy to Azure](https://aka.ms/deploytoazurebutton)](https://portal.azure.com/#create/Microsoft.Template/uri/https%3A%2F%2Fraw.githubusercontent.com%2FCyberlorians%2FCyberTriage%2Fmain%2Fdeploy%2Fcommercial%2Fcybertriage-full-deployment.json)

If Azure shows a quota error like `Dynamic VMs: 0`, pick a different region or ask the Azure subscription owner to raise Azure Functions Consumption quota. The SAS broker Function uses a Consumption hosting plan.

After the ARM deployment finishes, you still authorize API connections, create the watchlist, upload Live Response library files, and run one test.

## Step 2: Create The Evidence Storage Account

If you used the full commercial deployment button, this storage account and the `cybertriage-results` container were already created.

If you are deploying pieces separately, create the storage account yourself.

This storage account receives encrypted Cyber Triage output.

Recommended pilot settings:

```text
Public endpoint: Enabled
Default network action: Allow
Shared key access: Disabled
Container: cybertriage-results
```

Why shared key access is disabled:

The endpoint should not use storage account keys. It should use a short-lived SAS URL generated by the broker.

## Step 3: Create The SAS Broker Function

If you used the full commercial deployment button, this Function App was already created.

If you are deploying pieces separately, deploy:

```text
deploy/commercial/sas-broker-function.json
```

The SAS broker is a small Function App.

It has two endpoints:

```text
/api/health
/api/generate-cybertriagesas
```

The broker needs an app setting:

```text
BROKER_SHARED_SECRET = <long random value>
```

Do not commit this value to Git.

The broker also needs managed identity enabled.

The Function source comes from:

```text
src/SasBrokerNode
```

The repo root contains `.deployment`, which tells Azure App Service source deployment to use that folder.

## Step 4: Grant The Broker Storage Roles

If you used the full commercial deployment button with an `Owner` account, the template already assigned these roles.

If you are deploying pieces separately, or if the customer did not allow `Owner`, assign the roles with [scripts/Grant-CyberTriagePermissions.ps1](../scripts/Grant-CyberTriagePermissions.ps1) or use the manual steps in [setting-permissions-step-by-step.md](setting-permissions-step-by-step.md).

On the evidence storage account, grant the broker managed identity:

```text
Storage Blob Delegator
Storage Blob Data Contributor
```

On the Function host storage account, grant the Function managed identity the roles required by the hosting model. This is Azure Functions runtime storage, not the Sentinel watchlist queue. The full commercial template grants the baseline set:

```text
Storage Blob Data Contributor
Storage Queue Data Contributor
Storage Table Data Contributor
```

In the lab, these broader troubleshooting roles were also used while proving managed identity host storage:

```text
Storage Blob Data Owner
Storage Account Contributor
```

## Step 5: Test Broker Health

Run:

```powershell
Invoke-WebRequest -Uri 'https://<function-app>.azurewebsites.net/api/health'
```

Good result:

```text
HTTP 200
{"status":"ok"}
```

Bad result:

```text
503 Site Unavailable
```

If you see 503, check the Function host storage account. In the lab, host storage public access was disabled by policy, and that broke the Function.

## Step 6: Test SAS Generation Safely

Call the broker with the broker secret, but do not print the SAS URL.

Print only this kind of metadata:

```text
success
expiresOnUtc
storageAccountName
containerName
permissions
authMode
```

Good result:

```text
success = true
authMode = user_delegation_sas
```

## Step 7: Prepare MDE Live Response Library

Upload these files to the MDE Live Response Library:

```text
CyberTriageCollector.exe
Run-CyberTriage.ps1
```

`CyberTriageCollector.exe` is vendor supplied and is not committed to this repo.

`Run-CyberTriage.ps1` is in:

```text
src/LiveResponse/Run-CyberTriage.ps1
```

The Logic App later sends these commands:

```text
PutFile CyberTriageCollector.exe
RunScript Run-CyberTriage.ps1 -AzureSasUrl '<runtime SAS>' -Profile fast
```

## Step 8: Create The Sentinel Watchlist

Create a watchlist named:

```text
ForensicCollectQueue
```

Recommended columns:

```text
MdatpDeviceId
DeviceName
IncidentId
TagName
EnqueuedTime
Attempts
Status
RetryAfterUtc
LastAttemptUtc
LastError
BlockedActionId
```

A blank `Status` means pending.

Use this CSV template for manual upload:

```text
assets/watchlists/ForensicCollectQueue.csv
```

When Sentinel asks for the search key, choose:

```text
MdatpDeviceId
```

## Step 9: Deploy Collection Logic App

If you used the full commercial deployment button, this Logic App was already deployed as:

```text
CyberTriage-LiveResponse-Collection
```

If you are deploying pieces separately, deploy:


```text
deploy/commercial/cybertriage-live-response-collection.json
```

This playbook does the actual handoff to MDE Live Response.

Important parameter:

```text
SasBrokerUrl
```

This is secure. Do not print it in logs or commit it.

## Step 10: Deploy Set-CyberTriage Logic App

If you used the full commercial deployment button, this Logic App was already deployed as:

```text
Set-CyberTriage
```

If you are deploying pieces separately, deploy:


```text
deploy/commercial/set-cybertriage.json
```

This playbook adds the MDE tag and queue row.

Default tag:

```text
ForensicCollect
```

## Step 11: Deploy Queue Checker Logic App

If you used the full commercial deployment button, this Logic App was already deployed as:

```text
Check-CyberTriageQueue
```

If you are deploying pieces separately, deploy:


```text
deploy/commercial/check-cybertriage-queue.json
```

Deploy it disabled first.

Default behavior:

```text
Polls watchlist
Finds active/recent MDE devices
Deduplicates old rows
Calls the collection playbook
Leaves inactive devices queued
```

In the lab, the poll interval was changed to 60 minutes.

## Step 12: Authorize Connections

Open each Logic App in the Azure portal and check API connections.

Connections that may need attention:

```text
azuresentinel
wdatp
office365
azuremonitorlogs
azureblob
```

If a connection is not authorized, the Logic App can deploy but fail at runtime.

## Step 13: Verify Permissions

Follow [setting-permissions-step-by-step.md](setting-permissions-step-by-step.md).

If you used the full commercial deployment button with an `Owner` account, ARM already assigned the Azure RBAC roles. Use this step to verify the roles are present.

If `Owner` was not allowed, that page also shows both ways to set the permissions after deployment:

```text
Azure portal click-by-click
Azure CLI commands
```

Use [permissions.md](permissions.md) if you need the explanation of why each role is needed.

Do not skip verification.

The most common failure is a workflow that exists but cannot query logs, update watchlists, call MDE, or create SAS because the permissions were missing or the API connections were not authorized.

If the person doing the deployment cannot assign Azure RBAC roles, stop here and hand the admin this page:

```text
docs/admin-permission-handoff.md
```

The admin script is:

```text
scripts/Grant-CyberTriagePermissions.ps1
```

The script grants the SAS broker storage permissions and the Logic App workspace permissions after the resources exist.

## Step 14: Run A Controlled Test

Choose one MDE device that is active.

Check MDE status:

```text
healthStatus = Active
machineTags includes ForensicCollect
```

If the device is inactive, do not use it for the test.

## Step 15: Add A Queue Row

Use `Set-CyberTriage` from an incident or add a manual row for testing.

Minimum manual row:

```text
MdatpDeviceId = <MDE device ID>
DeviceName = <device name>
IncidentId = manual-test
TagName = ForensicCollect
EnqueuedTime = <current UTC time>
Attempts = 0
Status = blank or Pending
```

## Step 16: Run Queue Checker Manually

For the first test, run the queue checker manually.

Do not wait an hour.

Watch these actions:

```text
Run_Online_Queue_Query
Trigger_Collection
```

Then open the collection run and watch:

```text
Generate_CyberTriage_Sas
Run_LR_Collection
Remove_Tag
Delete_Watchlist_Item
```

## Step 17: Check MDE Machine Action

A successful handoff creates an MDE Live Response machine action.

Good signs:

```text
type = LiveResponse
status = Succeeded
commands = Completed
requestor = CyberTriage-LiveResponse-Collection
```

## Step 18: Check Storage

The first visible blob may be a small probe blob:

```text
cttest-blob
```

The real artifacts look like:

```text
cttout_<device>_<timestamp>.json.gz.enc.01
cttout_<device>_<timestamp>.json.gz.enc.02
```

The watchlist row may be deleted before the final blob appears. That is normal because the Logic App confirms Live Response handoff, not full collection completion.

## Step 19: Enable The Queue Checker

After one healthy test, enable the recurrence.

Recommended pilot interval:

```text
60 minutes
```

## Troubleshooting Quick Map

| Symptom | Likely Cause |
|---|---|
| `Generate_CyberTriage_Sas` fails | Broker unhealthy, storage unreachable, missing broker RBAC, bad broker secret. |
| Broker `/api/health` returns 503 | Function host storage inaccessible or Function runtime not healthy. |
| `Run_LR_Collection` skipped | SAS generation failed. |
| MDE action never appears | Live Response call did not happen. Check collection Logic App. |
| MDE action pending/fails | Endpoint may be inactive or another LR action is active. |
| Watchlist row remains | Device was inactive, not selected, blocked by retry, or collection failed before cleanup. |
| `cttest-blob` only | Probe worked, final collector upload has not landed yet. |
| Azure VM running but MDE inactive | Sense service/connectivity/onboarding issue on the endpoint. |
